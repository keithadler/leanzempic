# Benchmarks (2026-10-28, Apple M3, Lean 4.29.1, GHC 9.14.1 -O2)

This file is a log in the order the work happened. Early sections describe earlier states and are
superseded by later ones (for example the first "exact Nat" column and the "not measured" note
below). The README has the current consolidated picture.

Best of 3 wall-clock, same source functions (`examples/Bench.lean`), outputs agree.
Haskell columns are generated by leanzempic, not hand-written. The Haskell
binaries run with `-A128m` (bigger GC allocation area).

| Workload | Lean C backend | leanzempic, exact Nat | leanzempic, word Nat |
|---|---|---|---|
| sum loop, 2e8 iterations | 0.45 s | 1.30 s | **0.18 s** |
| collatz over 1..1e6 | 0.33 s | 1.64 s | **0.22 s** |
| build + sum 5e6-element list | 0.08 s | 0.29 s (no -A128m) | 0.09 s |

## Reading

* **Exact Nat (`runtime/Zempic/Nat/Exact.hs`)**: Nat is Haskell `Natural`, same semantics as Lean.
  3x to 5x slower than Lean. GHC's Core shows the loop is already tight (join
  points, specialization); the cost is out-of-line `naturalAdd`/`naturalSub`
  calls on a boxed sum type.
* **Word Nat (`runtime/Zempic/Nat/Word.hs`)**: Nat is `Word`; any result above 2^64-1 aborts
  with an error (it never wraps). GHC unboxes the loops fully: 2.5x and 1.5x
  faster than Lean's C backend. Only valid for programs whose numbers fit.
* **List workload**: mutator time is 0.045 s; the rest is GC copying the live list.
  `-A128m` removes most of it, leaving it level with Lean.
* (At this point fusion, `String`, `Array` and other types were not yet measured; see the later
  sections.)

## Reproduce

```sh
lake build bench
PATH=/opt/homebrew/bin:/usr/bin:/bin bench/build.sh Main
.lake/build/bin/bench 0; build/Main 0
```

(Run `build.sh` without Lean's toolchain on PATH, or GHC's C step picks up

# Fusion pipeline (`examples/Fusion.lean`)

`foldl (+) 0 (filter (y % 3 != 0) (map (x*x % 1000) (range n)))`. Best of 3 wall-clock.

| | n = 5e6 | n = 2e7 |
|---|---|---|
| Lean native, idiomatic `List.map/filter/foldl` | 0.10 s | 0.35 s |
| Lean native, via `Zempic.Fuse.*` (closure calls, no fusion) | 0.16 s | 0.60 s |
| leanzempic, word Nat, **fused** | **0.03 s** | **0.04 s** |
| leanzempic, exact Nat, **fused** | 0.12 s | 0.41 s |
| leanzempic, word Nat, ordinary Lean code (no `Zempic.Fuse`) | 0.37 s | 2.56 s |

Fused word mode allocates 58 KB in total for n = 2e7: the three intermediate lists
never exist. That is 9x faster than Lean's idiomatic version.

* **You must opt in.** Fusion happens only for pipelines written with `Zempic.Fuse.map/filter/foldl/range`.
  Ordinary Lean list code is compiled by Lean into private specialized loops before
  leanzempic sees it, so it stays unfused, and it is *slower* than Lean's own C there
  (2.56 s vs 0.35 s: GHC's copying GC on a live 2e7-element list).
* **Exact Nat** only breaks even (0.41 s vs 0.35 s): `Natural` arithmetic dominates once the lists are gone.
* Two things made it fire, both learned the hard way: lists must be native `[Any]` with no
  `unsafeCoerce` between stages (each cast is an opaque `case` that blocks GHC's rewrite
  rules), and `range` must be an explicit `build` (an `if n == 0` guard turned the producer
  into a join-point argument).
* Intermediate `let`s of fusible stages are emitted lazy, not strict. Results are identical
  for total functions; a panic inside a stage may happen in a different order or never.

## Auto-fusion (`examples/AutoFusion.lean`)

Same pipeline, written as plain `List.range n |>.map |>.filter |>.foldl`, with
`set_option zempic.fuse true` at the top of the file. n = 2e7, best of 3:

| | Time |
|---|---|
| Lean native, option off (idiomatic) | 0.38 s |
| Lean native, option on | 0.59 s |
| leanzempic, word Nat, auto-fused | **0.04 s** (57 KB allocated) |
| leanzempic, exact Nat, auto-fused | 0.40 s |

All four print the same value. The option costs native Lean about 55% on this
pipeline (closure calls replace specialized loops), which is why it is off by default.

# Auto mode: exact Nat at word speed

Default output now runs `Word` first and falls back to `Natural` on overflow, so the answers
are exact. Best of 3, same functions as above.

| Workload | Lean C backend | auto mode |
|---|---|---|
| sum loop, 2e8 iterations | 0.46 s | **0.18 s** |
| collatz over 1..1e6 | 0.33 s | **0.23 s** |
| build + sum 5e6-element list | 0.08 s | 0.10 s |
| fused pipeline, n = 2e7 (Fuse API or plain code + `zempic.fuse`) | 0.35 s | **0.04 s** |

Overflow check: `fact 25` (above 2^64) and `fact 3000 % 1000000007` both return the exact
value, the latter verified against Python (341406877). The earlier "exact Nat" column (3x to
5x slower than Lean) is superseded; `mode exact` still gives that behavior if you want it.

# More combinators (`examples/Combinators.lean`, `zempic.fuse` on)

`length`, `sum`, `take`, `append`, `foldr`, `any`, `all`, `zip` join `map`/`filter`/`foldl`/`range`.
Six pipelines over n = 5e6. Best of 3 wall-clock. Haskell is auto mode.

| Test | Lean plain | Lean, rewrite on | Haskell | Heap allocated (Haskell) |
|---|---|---|---|---|
| t1 range, filter, length | 0.09 s | 0.10 s | **0.03 s** | 61 KB |
| t2 range, map, sum | crashes | 0.11 s | **0.02 s** | 61 KB |
| t3 zip of two mapped ranges, map, foldl | crashes | 0.16 s | **0.08 s** | 560 MB |
| t4 range, take, strict foldr | 0.13 s | 0.13 s | **0.03 s** | 82 MB |
| t5 range any, range all | 0.15 s | 0.16 s | **0.03 s** | 61 KB |
| t6 range ++ range, length | 0.16 s | 0.16 s | **0.03 s** | 61 KB |

* "crashes": Lean's own `List.sum` and `List.zip` overflow the stack at 1e6 elements
  (`Stack overflow detected`). The Haskell build completes them.
* **Fully fused (about 61 KB for 5M elements):** length, sum, any, all, append, with `map`/`filter`/`range`.
* **Partly fused:** `zip` fuses only on its first list, so the second is built (560 MB). A
  strict `foldr` is not a loop (82 MB of stack). Both are limits of GHC's fusion rules, not of this backend.
* **Sharing blocks fusion, correctly.** `(List.range n).any f && (List.range n).all g` looked
  unfused (360 MB) because Lean's CSE merges the two `range n` into one shared list, and GHC will
  not recompute a shared list. With different producers it fuses. The example uses `range (n+1)`.
* Plain Lean, rewritten Lean and Haskell print identical values for all six at n = 100000.

# Typed structures (`examples/Structs.lean`)

User inductives are now real Haskell `data` types with typed, strict fields
(`ZC_Stats_mk !ZNat !ZNat !ZNat`, `ZC_Seg_mk !ZT_Pt !ZT_Pt`, `ZC_Tree_node !ZT_Tree !ZNat !ZT_Tree`),
so GHC unboxes them in loops. Best of 3, auto mode, n = 2e8 iterations.

| Test | Lean | Haskell | Speedup | Haskell heap (n = 2e7) |
|---|---|---|---|---|
| fold a 3-field record through a loop | 0.66 s | 0.31 s | 2.1x | 61 KB |
| walk a segment of two nested 2-field records | 0.58 s | 0.28 s | 2.1x | 61 KB |
| sum weights of an enum over a `for` loop | 0.42 s | 0.30 s | 1.4x | 61 KB |

The loops allocate nothing: the record lives in registers. Not faster (allocation-bound by
nature): a 1e6-element binary tree insert (0.09 s vs 0.08 s, 505 MB allocated) and an
`Option` search (0.08 s both). Lean already reuses a uniquely-held record in place, which is
why its record loops are fast too. All five tests print identical values at n = 1000 and 100000.

# Fixed-width integers and arrays

**Integers** (`examples/Ints.lean`, n = 2e8, best of 3). Identical values to Lean, including
shifts at and above the width, division by zero and wraparound.

| Test | Lean | Haskell | Speedup | Haskell heap |
|---|---|---|---|---|
| 64-bit FNV hash, one mutable variable | 0.34 s | 0.32 s | 1.1x | 62 KB |
| UInt32 to UInt8/16/64/USize conversions | 0.90 s | 0.63 s | 1.4x | 62 KB |
| Char arithmetic (n = 1e8) | 0.41 s | 0.27 s | 1.5x | 62 KB |
| UInt8 arithmetic, two mutable variables | 1.50 s | 0.83 s | 1.8x | 6.4 GB |
| xorshift32, two mutable variables | 1.31 s | 1.21 s | 1.1x | 6.4 GB |

The two tests that allocated 6.4 GB carry two mutable variables through a `for` loop in Lean's
polymorphic `MProd` structure, whose fields were boxed `Any`. Generic structures are now typed
(next section): those two rows became 61 KB and 2.7x and 1.6x.

**Arrays** (`examples/Arrays.lean`). Here Lean wins, and clearly. Lean mutates an array in place
when it holds the only reference, which it knows from reference counts. GHC has none, so the
Haskell side uses a persistent array (Baker's scheme: a mutable buffer plus undo records), which
is correct for every use but pays for it.

| Test | n | Lean | Haskell (Baker) | Haskell (first try: Data.Sequence) |
|---|---|---|---|---|
| sieve of Eratosthenes | 5e6 | 0.11 s | 0.36 s | 4.66 s |
| push, then in-place prefix sums | 3e6 | 0.04 s | 0.30 s | 1.29 s |
| map and fold | 3e6 | 0.05 s | 0.31 s | 1.73 s |
| reverse with swaps | 2e6 | 0.05 s | 0.14 s | 3.20 s |
| stack of push and pop | 5e6 | 0.08 s | 0.21 s | 0.14 s |

So arrays are 3x to 10x slower than Lean's, down from 15x to 90x with the sequence. Every array
test matches Lean's value. Closing the gap needs ownership information (which array is
uniquely held), which the Haskell backend does not have.

**Strings** (`examples/Strings.lean`). A Lean string is a shared UTF-8 buffer (every version is a
prefix of one buffer; appending to the newest version writes in place, appending to an older one
copies). My first version, Haskell `Text`, copied on every push: 100,000 pushes took 6.83 s
against Lean's 0.02 s. Same tests, best of 3:

| Test | n | Lean | Haskell (buffer) | Haskell (Text, first try) |
|---|---|---|---|---|
| push characters, then length and byte size | 1e5 | 0.02 s | 0.02 s | 6.83 s |
| push characters | 1e7 | 0.05 s | 0.18 s | not run |
| append `toString i ++ ","` | 1e5 | 0.03 s | 0.03 s | 1.65 s |
| append `toString i ++ ","` | 3e6 | 0.12 s | 0.50 s | not run |
| equality and ordering of `toString` pairs | 1e6 | 0.07 s | 0.24 s | 0.08 s |
| `toList`, `ofList`, reverse | 2e6 | 0.02 s | 0.02 s | 0.02 s |
| length and byte size of non-ASCII text | 2e7 | 0.02 s | 0.02 s | 0.02 s |

Small strings are level with Lean; at millions of operations the Haskell side is 3x to 4x slower,
mostly from allocating a fresh buffer for each short string. All five tests print Lean's values,
including text whose character count differs from its byte size.

# Generic structures typed by their type arguments (`examples/Generics.lean`)

A generic inductive is now a polymorphic Haskell type with strict fields, for example
`data ZT_MProd a0 a1 = ZC_MProd_mk !a0 !a1`. Every instantiation has the same heap layout, so a
value can pass through an out-of-line generic function and come back with no conversion, and GHC
unboxes the fields wherever it knows the concrete types. (A separate Haskell type per instantiation
would make such a call read the wrong layout.) Best of 3, auto mode.

| Test | n | Lean | Haskell | Speedup | Haskell heap |
|---|---|---|---|---|---|
| UInt8 arithmetic, two mutable variables | 2e8 | 1.56 s | 0.57 s | 2.7x | 6.4 GB to **61 KB** |
| xorshift32, two mutable variables | 2e8 | 1.32 s | 0.85 s | 1.6x | 6.4 GB to **61 KB** |
| three mutable variables (UInt8, UInt32, Nat, Bool) | 2e8 | 1.03 s | 0.60 s | 1.7x | **61 KB** |
| swap `Pair`s of three different types through one `@[noinline]` generic function | 2e7 | 0.55 s | 0.08 s | 6.6x | 320 MB |
| a list, an array and an `Option` of pairs | 2e6 | 0.12 s | 0.35 s | 0.3x | 735 MB |
| binary trees of pairs, keyed by a closure | 3e5 | 0.79 s | 1.29 s | 0.6x | 3.6 GB |

The last two are slower than Lean: they are dominated by list and persistent-array traffic and by
calling a closure from an out-of-line generic function, not by the structures. All four tests print
Lean's values at n = 10, 1000 and 20000.

# Ownership analysis: in-place arrays (`Zempic/Own.lean`)

Lean updates an array in place when it holds the only reference, which it knows from reference
counts. GHC has none, so a static analysis over LCNF proves it instead: an operation updates in
place only if its array is uniquely held and nothing can see it afterwards. Everything else keeps
the persistent array. Loop state is tracked through constructor cells (a `for` loop with two mutable
variables carries them in an `MProd`), and facts about function parameters, results and join points
are met over every call site to a fixpoint. Roots, functions used as values, partial applications,
closure captures, and any use the analysis does not recognize all forget ownership.

Best of 3, auto mode. "Before" is the persistent array alone.

| Test | n | Lean | Before | With ownership | Heap before to after |
|---|---|---|---|---|---|
| sieve of Eratosthenes | 5e6 | 0.10 s | 0.28 s | **0.17 s** | 1.20 GB to 40 MB |
| push, then in-place prefix sums | 3e6 | 0.04 s | 0.29 s | **0.11 s** | 906 MB to 283 MB |
| map and fold | 3e6 | 0.05 s | 0.30 s | **0.12 s** | 1.21 GB to 275 MB |
| reverse with swaps | 2e6 | 0.04 s | 0.13 s | **0.05 s** | 609 MB to 121 MB |
| stack of push and pop | 5e6 | 0.08 s | 0.20 s | **0.13 s** | 753 MB (unchanged) |
| sieve | 2e7 | 0.38 s | not run | 0.72 s | 160 MB |
| prefix sums | 1e7 | 0.08 s | not run | 0.51 s | 988 MB |

The gap to Lean closed from 3x to 10x down to about 1x to 3x. The reverse is level with Lean.
It is still slower: values are still boxed `Any`, and unmatched constructs fall back to the
persistent array. The stack test is unchanged because its pushes and pops are interleaved with
reads of the back element in a way the analysis cannot prove.

**Soundness is the point, so it was tested hard** (`examples/Aliasing.lean`, 15 programs, 8 sizes
each, every value equal to Lean's): updates while the old array is still read, the same array
given to a function by one caller that keeps it and another that does not, two identical
constructions that must not become one array, closures and structures holding the array while it
is updated, nested arrays, arrays in lists, join points merging old and new versions, and loops
that keep a snapshot. I then broke the analysis on purpose five ways and checked the tests notice:

| Deliberate bug | Caught |
|---|---|
| ignore whether the array is used later | yes |
| hand over ownership though the caller still uses the array | yes |
| partial application keeps ownership of its arguments | yes |
| constructor application keeps ownership of the stored array | yes |
| ignore closure capture in a local function | **no** |

The last rule guards a case that never arises: Lean's compiler lifts every closure I could write
into a separate function (covered by the partial-application rule above), so a local-function node
with a captured array does not occur in these programs. The rule stays as defence.
Two further safeguards: modules that use in-place updates are compiled with `-fno-cse
-fno-full-laziness` so GHC cannot share two array constructions or float one to top level, and each
in-place primitive checks that its array is the live version and otherwise falls back to the
persistent operation. `set_option zempic.own false` turns the analysis off.

# Strings, second pass: a runtime fix, not an analysis (`runtime/Zempic/Str.hs`)

I planned to extend the ownership analysis to strings. Measuring first changed the plan. A bare
Haskell loop calling the string push 10 million times allocated exactly what the generated program
did (1.71 GB, 0.17 s): all of the cost was inside the push itself, 171 bytes per call against an
intrinsic 32 (one record). It was overhead in my implementation: a closure per append,
`withForeignPtr` bookkeeping, and a boxed counter in a separate mutable cell. Moving the byte
count into the buffer, giving the one-byte case a closure-free path, and writing decimal digits
straight into a fresh buffer (instead of through `Text` and `ByteString`) fixed it:

| Test | n | Lean | Before | After |
|---|---|---|---|---|
| push characters | 1e7 | 0.05 s | 0.18 s, 1.71 GB | **0.06 s**, 353 MB |
| append `toString i ++ ","` | 3e6 | 0.12 s | 0.50 s | **0.23 s** |
| equality and ordering of `toString` pairs | 1e6 | 0.07 s | 0.24 s | **0.09 s** |
| `toList`, `ofList`, reverse | 2e6 | 0.02 s | 0.02 s | 0.02 s |
| length and byte size of non-ASCII text | 2e7 | 0.02 s | 0.02 s | 0.02 s |

Pushing is now level with Lean and the other string tests are within about 2x. An ownership
analysis would save only the small record per push, where the loop is already at parity, and would
add soundness risk, so strings stay persistent (every version a prefix of a shared buffer).

The buffer's one subtle rule is that an append may write in place only if the string is the newest
version of its buffer, and otherwise must copy. `examples/StringAliasing.lean` (6 programs, 7
sizes each) pushes to an old version twice, appends strings to themselves, extends one literal in
several places, grows across the starting capacity with multi-byte characters, keeps snapshots,
and compares versions that share a buffer; all match Lean. Removing the newest-version check from
either the one-byte push or the general append makes every size differ, so the tests would notice.
`panicCore` is a runtime primitive that returns the default value silently (Lean also prints a
message to stderr).

**A mistake worth recording.** While writing these tests both programs failed to build, both
outputs were empty, and my comparison called two empty files "identical". Every comparison in
`tests/run.sh` now goes through `eq`, which fails on empty output.


## A proved development: AES-256 from lean-aes

Source: `keithadler/lean-aes`, AES-256 written from FIPS-197 with its correctness and the wide-trail
bound proved (353 declarations, re-checked by Tenet). The four spec files (`Basic`, `GF`, `SBox`,
`Spec`, about 700 lines including the proofs of the field laws) are copied unchanged into
`bench/aes/AES/` and build under Lean 4.29.1 with all their proofs. The benchmark encrypts one block
`n` times in a row under one key, each output feeding the next, and prints a fingerprint of the last
block. It is the specification as written, not a tuned implementation: it recomputes the key
schedule for every block, multiplies in GF(2^8) with a bit loop, and looks bytes up in a 256-entry
`Array`. `bench/aes/run.sh N` builds both sides, checks they agree, and times them;
`tools/aes_oracle.py` computes the same fingerprint with OpenSSL (six seed and length combinations
agree with both Lean and Haskell; three are in `tests/run.sh`).

| Run | n | Lean C | leanzempic |
|---|---|---|---|
| first attempt, key as a 256-bit literal | 1e6 | 8.7 s | 43.6 s (5x slower) |
| key and block built from bytes, no unrolling | 1e5 | 0.85 s | 2.18 s |
| same, with recursion unrolling | 1e5 | 0.86 s | 1.54 s |
| same, with recursion unrolling | 1e6 | 8.81 s | 15.63 s (1.8x slower) |

What each step taught:

1. **A 256-bit literal silently put the whole program on the slow path.** `Key.ofNat 0x0001...1f`
   contains a number above 2^64. In the `Word` fast path that literal is `overflow`, so the call
   throws `ZOverflow` and auto mode reruns everything in exact `Natural` arithmetic, including the
   hot loop. The answer was right and the speed was 5x worse, with nothing to say why. Editing the
   generated fast module changed nothing, which is how I found it. Building the key from bytes
   (all values small) keeps the loop on `Word`. This is a real limitation of auto mode: the
   fallback is per call, not per use.
2. **`abbrev` types were boxed.** `Byte` is `abbrev Byte := UInt8`, and structure fields of a
   reducible alias were typed `Any`, so every byte was boxed. The type mapping now unfolds reducible
   aliases (measured on the slow exact path only: 4.47 s to 3.97 s at 1e5).
3. **GHC does not unroll recursion; the C compiler does.** `mulLoop 8 a b 0` is a recursive loop with a
   literal count. Profiled, it took 52% of the time and 79% of the allocation (about 6,600 iterations
   per block). A hand-unrolled `mul` brought 2.27 s to 1.19 s and 6.1 GB of allocation to 0.8 GB.
   The emitter now specializes a self-recursive call whose `Nat` argument is a literal up to
   `zempic.unroll` (default 16): it tracks literal values through `Nat.add/sub/mul` and comparisons,
   drops the branch of any test of known numbers, and prints one `INLINE` copy per count
   (`z_AES_mulLoop_u8_x_x_x`, `..._u7_...`, down to the base case), so GHC sees straight-line code.
4. **Unrolling needs a size budget.** The first version also unrolled the 14-round loop, with each
   round containing 16 unrolled multiplies. With a limit of 8, GHC ran for over 12 minutes on one
   module. A function is now unrolled only if its body plus what it calls (three levels deep) has at
   most 60 bindings, so small leaf loops unroll and the round loop does not. At most 64 copies per
   function.

Things that did not help, measured by patching the generated Haskell by hand: replacing the
persistent-array S-box with an immutable unboxed array (2.27 s to 2.11 s, within noise of the
remaining overhead), and rewriting `mulLoop` as a tighter local loop (no change).

Remaining gap, 1.8x. I did not profile this further; the likely causes, unmeasured, are boxed `Any` elements on the S-box lookups, the key schedule held as a `List`
of words rebuilt for every block, and `Word.map sbox` / `mapCols mixColumn` going through closures.
The honest summary is that a proved, byte-oriented, table-driven cipher is a workload where
the C backend wins, and where this project's strengths (Nat loops, fusion) do not apply.


## The garden, profiled (2026-10-28)

`garden/perf.py` builds each garden program with Lean's C backend and with leanzempic, checks the
answers match, and times both (best of 3, one at a time, 20-second cap). Programs whose native time
is a few milliseconds even at a large `n` do not actually scale with `n` (their ratio is Haskell
process start-up, about 15 ms with `-A128m`) and are not reported. Of the rest:

| Program | n | Lean C | leanzempic | Ratio |
|---|---|---|---|---|
| float arithmetic loop | 5e6 | 0.44 s | 0.05 s | 0.10 |
| `Int` arithmetic fold | 3e6 | 1.11 s | 0.26 s | 0.23 |
| binary tree map and sum | 2e5 | 2.38 s | 1.07 s | 0.45 |
| record update loop | 5e6 | 0.10 s | 0.10 s | 0.96 |
| `while` loop | 3e7 | 0.17 s | 0.15 s | 0.86 |
| `Option` chain, `StateM` loop | 5e6, 3e6 | 0.12, 0.04 s | 0.10, 0.03 s | 0.8 |
| list merge sort | 3e5 | 0.08 s | 0.10 s | 1.15 |
| `Array.qsort` | 3e5 | 0.26 s | 0.39 s | 1.5 |
| string building (`toString`, append) | 1e6 | 0.045 s | 0.08 s | 1.8 |
| `HashSet` inserts | 2e6 | 0.10 s | 0.19 s | 1.9 |
| tuple-state fold | 5e6 | 0.10 s | 0.28 s | 2.7 |
| list of `UInt8` hashed (FNV) | 3e6 | 0.05 s | 0.16 s | 3.0 |
| `HashMap` inserts | 3e6 | 0.07 s | 0.22 s | 3.0 |
| string iteration (`foldl` over chars) | 1e6 | 0.10 s | 0.35 s | 3.6 |
| `String.splitOn` | 1e6 | 0.20 s | 0.66 s | 3.3 |
| list functions (zip, filterMap, foldr, ...) | 1e6 | 0.06 s | 0.26 s | 4.4 |
| array map/filter/zip/fold | 2e6 | 0.05 s | 0.26 s | 5.7 |
| array index loop (`uget`, `a[i]'h`) | 1.5e7 | 0.14 s | 0.9 s | 6 to 7 |
| `insertionSort` on a shared array | 3e3 | 0.008 s | 0.17 s | 21 |

**The pattern.** Arithmetic, records, `Int`, `Float` and trees are level or faster. Everything that
holds many boxed elements (lists, arrays, hash maps, strings built from pieces) is 2x to 7x slower,
and the one case where an array is both shared and mutated in a loop is about 5x to 9x (lazy copies).

**Why, from the profiles.**

* **Garbage collection is about half the time of the slow list and array programs.** GHC's copying
  collector moves every live boxed element; Lean frees a cons cell the moment its count reaches zero
  and reuses it. Measured on `array_funcs`, `tuples`, `uint64_hash` and `list_funcs`, the
  mutator and the collector each take roughly half the run. A bigger allocation area helps the
  collector directly: `-A256m -O1g` (or `-H1g`) gave 0.27 to 0.22 s, 0.15 to 0.10 s, 0.26 to 0.17 s
  and 0.35 to 0.29 s respectively, with no change to the generated code. `--nonmoving-gc`, `-c`,
  `-G3` and `-F4` did nothing. Smaller areas (`-A32m`, `-A64m`) were worse.
* **A shared array that a loop mutates is the worst case.** Lean copies the array once on the first
  write and then updates it in place. The ownership analysis cannot prove an array passed in by a
  caller that keeps using it is unshared, so the whole loop runs on the persistent array, which
  allocates a new version (about 100 bytes) per operation. `insertionSort` called on an array that
  is used afterwards is the example (4.5M swaps). Copying such an array once on entry would match
  Lean, but it would change the analysis the in-place updates rest on, and it does not help when
  the array is carried in a loop-state cell. It is the main item on the roadmap, not done.
* **Fusion does not help here.** With `zempic.fuse true`, `uint64_hash`, `list_funcs`, `tuples`,
  `closures` and `list_mergesort` changed by less than the noise: Lean's own `List.map` and
  friends have already been specialized to loops by the time the pass runs.

**What was optimized in this round** (each measured on the program named):

| Change | Before | After |
|---|---|---|
| a swap is one array version with one undo record, not two chained sets | `insertionSort` 0.535 s | 0.170 s |
| growing a persistent array copies with a strict loop, not a list | `array_funcs` 0.351 s | 0.26 s |
| one strict read per character instead of three; `appendWith` inlined | `string_chars` 0.454 s, `string_build` 0.116 s | 0.345 s, 0.080 s |
| `-A256m -O1g` instead of `-A128m` (RTS option, not code) | list and array programs | 25 to 40% faster |

Tried and dropped: inlining the array read primitives (no change), a tighter `mulLoop` (no change),
an unboxed S-box table (7%, below the noise of the rest), `zempic.fuse` (no change).


## Narrow integer arrays and the real-world `qsort`: 2.83x to 1.58x (2026-10-29)

`bench/realworld` `qsort` (Lean's own benchmark, `UInt32` elements, `partitionAux` over an `Array UInt32`,
n = 300) was 2.83x slower than Lean's C backend. Reading the generated STG showed what the per-step cost was:
every `a[j]!` went through the generic `Any` reader (`arrGetD`), which boxed the `UInt32` (a `W32#`, 16 bytes)
and was un-boxed again by the caller, with the element's inhabited default boxed too. The swaps were a call
to a `NOINLINE` primitive. Same machine, A/B against a worktree of `main`, interleaved, best of 5; the CPU
time is user plus system, and `instructions retired` and `cycles elapsed` come from `/usr/bin/time -l`,
which are steadier than seconds on a loaded machine.

| `qsort`, default settings | before | after |
|---|---|---|
| CPU, best of 5 (native Lean C: 0.78 s) | 2.21 s, 2.83x | 1.23 s, 1.58x |
| CPU, recommended settings (`zempic.fuse`, `-A256m -O1g`) | 2.20 s, 2.86x | 1.24 s, 1.61x |
| allocated | 5283 MB | 1835 MB |
| instructions retired (native: 15.1 G) | 41.5 G, 2.74x | 21.9 G, 1.45x |

What changed:

* **Narrow-typed element access.** `UInt8/16/32/64` (and `Char`) reads, pushes and in-place writes are chosen
  by the emitter from the Haskell type of the element, as the `Word` ones already were: `arrGetD32`,
  `arrGetI32`, `arrUGet32`, `arrPushU32`, `arrSetU32`, `arrUSetU32`, and the 8, 16 and 64 bit versions. The
  common case (a live buffer of the matching kind) is read or written in line with no box; all else goes to a
  `NOINLINE` function using the generic operations. The `partitionAux` loop now allocates nothing per step.
  This is what takes `qsort` from 5283 MB to 1627 MB.
* **In-line swaps** for arrays of a known word-like element type (`arrSwapU8` ... `arrSwapUW`), and a bounds
  check that is one unsigned comparison. A `Word` index is not clamped in word mode.
* **The caller's array is handed back.** The first version of the narrow swap returned its `Arr` argument,
  and GHC rebuilt the 24-byte record on every swap because the argument had been unpacked by the worker:
  allocation went back up to 3568 MB and the speedup shrank. The fix is for the in-line paths to return a
  flag and for the wrapper to return the `Any` it was given (`aSwapF32`, `aSetF32`). Before the later changes
  (unsigned bounds, the lazy default on the slow path) allocation was 1627 MB; after the fix it is 1835 MB.
  I did not find where the extra 208 MB comes from.
* **Block-copy growth.** `bufGrow` copies with `copyMutableByteArray#` / `copyMutableArray#` and clears only the
  tail, instead of an element loop after filling the whole new buffer. Prefix sums (10M pushes) 0.488 to
  0.456 G cycles.
* `UNPACK` on the buffer constructors (one pointer less per access). Alone it moved `qsort` from 1.82x to
  1.75x of native in cycles in a noisy run; kept, because it does not hurt, but that is within noise.

What did not work or was not done:

* The returned pair of `partitionAux` (a `W32#` and a tuple per call, about 40 bytes) is not unboxed: the
  function returns `Any` (the pair coerced), so GHC's CPR analysis has no product to unbox. Ticky counts at
  n = 100 put it at about a third of what `qsort` still allocates; the rest is the 24-byte `Arr` of each push in
  `mkRandomArray` and the `MProd` of each step of `isSorted`. Fixing the pair needs the emitter to give
  pair-returning functions a typed result, which is a larger change than this one.
* (b), `Array.foldl`/`foldlM` loops: `Nat` and `USize` elements already used `arrUGetW` on `main`
  (`mapFold` reads through it); what was missing was the other widths, which the narrow reads cover
  (`arrUGet32` and friends, exercised by `array_narrow_paths`). There was nothing further to change for
  `Nat`.
* (c), the 24-byte `Arr` per in-place push is not removed. The length lives in the immutable `Arr`, and
  every version needs its own, so returning the same record would need a mutable length and a redesign of
  the undo records; one `Word` set returning the caller's array (the same trick as the swap) changed neither
  allocation (508 MB) nor time on Prefix sums, so I reverted it.
* `Float` elements have no unboxed buffer kind (the kinds are `Word8/16/32/64`, `Word`, `Bool`), so they
  are untouched.
* What remains of the 1.58x is structural: each access is a `readMutVar#`, a tag test on `Direct`, a tag test
  on the buffer kind, then the load, where native Lean does one load. Hoisting that out of a loop whose array
  is owned would need the emitter to pass the buffer into the loop.

Other `bench/realworld` programs, before and after, same method (cycles elapsed relative to native; these
programs do not use the changed paths, and their allocation is identical): `binarytrees` 0.73x / 0.73x,
`const_fold` 1.01x / 1.03x (instructions retired identical: layout noise), `deriv` 1.16x / 1.16x,
`unionfind` 1.16x / 1.16x, `nat_repr` 1.13x / 1.13x (default settings; `rbmap` does not compile on this
branch, a separate fix). Chart rows (cycles elapsed relative to native, before / after; the chart itself was
not refreshed, and differences of 0.03 are noise): Sieve 1.21x / 1.18x, Prefix sums 1.77x / 1.57x, Array map
and fold 0.91x / 0.89x, Reverse by swaps 0.74x / 0.67x, Push and pop stack 1.05x / 1.00x. Garden:
`array_funcs` instructions retired 2.39 G to 2.18 G, `array_misc` 0.58 G to 0.48 G, `array_qsort` and
`uint64_hash` unchanged.

Tests: `tests/PropTests.hs` `arrNarrow` drives each width on a boxed buffer and on a buffer of the matching
kind (push, set, pop, swap, get, lazy handle, stale versions, indexes -1, `minBound`, `maxBound`, 2^63, 2^64,
2^70) against a list model, in word and exact mode. Mutations caught: a swap that drops one write, a set at
the wrong slot, a get at the wrong slot, a push that bumps the length by two, an off-by-one in the bounds
check, a signed instead of unsigned bounds check, a slow-path read off by one, a slow path that forces the
default, a growth copy that is one element short (it crashes). A mutation that fills the grown tail with
garbage is not caught and is not observable: the tail is never read before it is written. New garden program
`array_narrow_paths` (UInt8/16/32/64 and `Char`, in place and on a kept snapshot, `set!`, swaps, `for` loops).

## Array reads and writes without boxes: `array_funcs` 3.9x to 2.5x (2026-10-29)

`array_funcs` (range, map, filter, zip, foldl, any/all, contains, reverse, extract, append at n = 2e6)
was 3.9x slower than Lean's C backend after the dead-store peephole. Same machine, same load, A/B in two
worktrees, best of 11 CPU seconds and exact allocation:

| | before | after |
|---|---|---|
| allocated | 485.7 MB | 329.4 MB |
| CPU, best of 11 | 0.176 s | 0.107 s |
| `garden/perf.py` ratio vs Lean C | 3.9x (4.3x on the first run) | 2.5x |

Each phase alone (allocation above the 16 MB buffer of the range itself; the process start is 13 ms of
every run at `-A128m`):

| phase | before | after |
|---|---|---|
| `Array.range` 2e6 | 89 MB | 0 |
| `map (* 3)` | 64 MB | 0 |
| `foldl`, `any`, `all`, `contains` | 64 MB | 0 |
| `filter (% 2 == 0)` | 40 MB | 40 MB (the 24-byte `Arr` of each push, plus buffer doubling) |
| `zip` then `map` over pairs | 153 MB | 113 MB |
| `reverse` | 56 MB | 40 MB |
| `a ++ b` | 98 MB | 160 MB for `a ++ a` (see below) |

What changed:

* `Array.range` is a primitive: one pass filling a `Word` buffer in word mode, instead of `ofFn` calling a
  closure and boxing each index.
* `Word`-typed reads, pushes and in-place writes. When the emitter can see the element is a `Word`
  (a `Nat` in word mode, or a `USize`) it calls `arrUGetW`, `arrPushUW`, `arrUSetBUW` and so on, which read
  and write a word buffer with no box. Inside Lean's in-place `Array.map` the read's type is hidden by the
  view as `NonScalar`, so it is typed by a later use as a `Nat` argument instead.
* Swaps exchange raw elements (no box per swap), and the read-then-push of `append`/`extract` moves the
  element from buffer to buffer (`aPushFromU`).

**The earlier "typed array reads" experiment failed for a reason I can now name.** The README records
that allocation went up (534 MB to 646 MB) and that I did not find out why. Allocation went up again on
my first attempt here (485 MB to 537 MB, then 570 MB), and reading the STG showed four separate causes,
all GHC boxity, none of them in the array code itself:

1. A `NOINLINE` primitive that returns a `Word` returns it boxed (no unboxed return), so every typed read
   still built a `W#`. Fix: the read is a `NOINLINE` worker in `State#` style returning `Word#`, wrapped
   by an `INLINE` function, so the call site gets a register.
2. Arguments that any path uses boxed stay boxed in the worker. The slow paths (`aSet` on a stale
   version, a write into a non-word buffer) used the `Word` or the index as a box, which made the fast path
   take boxed `Int`s and `Word`s: 16 bytes per call, twice. Fix: bang the arguments, and put every use
   that needs a box in a `NOINLINE` function that takes `Word#` and `Int#`.
3. `error "index out of range"` as the default of an inlined read was rebuilt as a thunk on every
   iteration (24 bytes). Fix: one shared top-level thunk.
4. Strictness was missing on the generic in-place primitives too (`arrSwapPU` boxed both indices).

Not kept:

* An inline fast path for the common read (live version, word buffer) in `aGetWI`: allocation 329 MB to
  361 MB, no time gain. Reverted.
* A larger initial capacity for `mkEmpty` (clamp 1M to 16M elements): no effect on this program. Reverted.
* Smaller `-A` (16m, 4m, 1m) is slower, 0.17 to 0.19 s against 0.11 s: with a 128 MB nursery nothing is
  collected at all (GC time 0.000 s), so the cost left is bytes streamed through the nursery.

What is left, in order: the 24-byte `Arr` each in-place push returns (its length is an immutable field), the
boxes and pairs of `zip` (the polymorphic `Array.zip` reads `Any`), and `a ++ b`, whose in-place push
loop starts from a lazy copy and doubles twice. `a ++ a` allocates more than before (160 MB against
128 MB) because the move is a `NOINLINE` call per element that the old read-then-push pair did not need;
the time is level.

Other array programs, `garden/perf.py` ratio against Lean C, same load, before then after: `usize_loop` 8.2x to
1.6x, `subtype_index` 5.2x to 1.6x, `array_qsort` 1.60x to 1.53x, `prod_arrays` 2.3x to 1.9x,
`array_2d_loop` 5.0x to 4.4x, `shared_twice` 3.7x to 2.4x, `shared_rare_write` 2.3x to 2.1x, `bytearray`
2.0x to 1.9x, `array_misc` 5.2x to 5.3x (level; both runs are 11 to 17 ms of Lean time, so ratios there
are noisy).

**Merged with two other branches that touched the same code (2026-10-29).** One made `Nat` reads and
writes in the Prefix-sums benchmark unboxed with `runRW#` and an in-line fast path; the other made the
index arguments of the generic primitives strict (`array_misc`). Combined, every row is at least as good
as its best single-branch number (allocation exact, CPU best of 11, same load):

| row | base | each branch alone | merged |
|---|---|---|---|
| Prefix sums (`examples/Arrays.lean`, n = 1e7) | 1308 MB, 3.6x | 508 MB, 1.7x (prefix branch); 668 MB, 2.6x (this branch alone) | 508 MB, 1.7x |
| `array_misc` | 115.6 MB, 0.046 s | 0.7 MB, 0.035 s (strict-index branch); 82.5 MB (this branch alone) | 0.7 MB, 0.025 s |
| `array_funcs` | 485.7 MB, 0.175 s | 429.7 MB, 0.177 s (prefix branch); 329.4 MB, 0.107 s (this branch alone) | 321.4 MB, 0.099 s |

What each side was missing: this branch's reads were a `NOINLINE` call (one call per element, and a
boxed default for `a[i]!` built in every iteration, 16 bytes), and its generic primitives still boxed
the index; the other side had no `Array.range`, no `UInt8`/`Bool` handling, and boxed the pushes of
`filter`. One implementation of each primitive is kept, the superset, with the in-line fast path and
the strict `Word#` default of the other.

**A bug found on the way, not fixed here.** Two `Array.mkEmpty 4` of different element types in one function
are merged by Lean's common-subexpression elimination into one variable, and the buffer kind follows the
first one's type. Pushing `Nat`s into an array that began as `Array UInt8` truncates them to bytes. The
baseline commit does the same (`garden/programs.py` `array_word_paths` first drew it out). The test avoids it
with different capacities.

## Ideas from tenet-hs, tried (2026-10-29)

tenet-hs (an independent Lean kernel in Haskell, same author) got a 2.5x memory cut and large speed-ups
from packed two-word node metadata, `UNPACK`ed strict fields, unboxed key arrays and mutable arrays in
place of persistent maps. Which of that carries over to generated code:

* **`-funbox-strict-fields` on generated modules: no effect.** `struct_update`, `tuples`,
  `functor_tree`, `typeclass`, `hashmap` all within noise. GHC already unpacks small strict fields
  (`Word`, `Word8`, ...), and the fields that are not small are boxed `Any` on purpose.
* **Unboxed array buffers chosen from the element type: no gain, and unsafe as built.** A
  microbenchmark of a 4M-element fill, three read-modify-write passes and a sum takes 0.47 s with boxed
  elements (0.56 s of it garbage collection) and 0.03 s with an unboxed array, which is the upper bound.
  I built the real thing: the emitter picked a buffer kind (`Word8` ... `Word`, `Bool`) from the array's
  Lean type, every operation dispatched on the buffer, and a property test checked all seven kinds
  against a model (a deliberate bug in the growth copy was caught). On `array_funcs` the peak residency
  fell from 378 MB to 133 MB and the collector's share shrank, but the run time stayed at 0.26 s, and
  `usize_loop`, `subtype_index`, `array_misc` did not move either. The cost is in the persistent
  machinery on every access (version check, dispatch, re-boxing a read element), not in the collector.
  It also has a soundness hole: Lean's own library writes placeholder values into arrays
  (`Array.modify`, `modifyM`, `swapAt` write `box(0)` and write the element back later) and
  `Array.mapMUnsafe` changes the element type of an array in place, so a typed buffer can be handed a
  value it cannot hold. Making that safe needs a static kind at every access site and typed in-place
  primitives that bypass the generic path, which is a larger redesign than this round. **Reverted.**
* **What did carry over, already in:** mutable arrays in place of persistent structures (`Zempic.Arr`),
  strict fields and strict counters, a large allocation area (`-A256m -O1g`), and the habit of
  profiling before changing anything.


## Fusion done right, a GHC panic, and the heap census (2026-10-29)

**An invalid test, corrected.** The earlier "fusion changes nothing" result set `zempic.fuse true`
just before `#zempic`. The pass runs when Lean compiles the definitions, so the option has to come
first. With it set correctly, best of 3, identical answers:

| Program | n | plain | fused |
|---|---|---|---|
| list of `UInt8` hashed (FNV) | 3e6 | 0.15 s | 0.03 s |
| tuple-state fold | 5e6 | 0.26 s | 0.08 s |
| `Int` list work | 1e6 | 0.30 s | 0.15 s |
| sum-type fold | 3e6 | 0.14 s | 0.06 s |
| `Option` chain | 5e6 | 0.09 s | 0.03 s |
| list functions (zip, filterMap, foldr, ...) | 1e6 | 0.26 s | 0.18 s |
| closures | 1e6 | 0.04 s | 0.03 s |
| list merge sort | 3e5 | 0.09 s | 0.12 s (slower) |

The reason is what tenet-hs found about copying collectors: live data is the cost, not allocation.
A fused pipeline never builds the intermediate list, so there is nothing for the collector to copy.
All 109 garden programs agree with native Lean with fusion on (`GARDEN_FUSE=1`).

**A GHC panic, found by fusion.** `list_funcs` with fusion made GHC 9.14.1 panic ("the 'impossible'
happened", `StgToCmm.Env: variable not found co5_Xc`). It was deterministic for a given invocation but
changed with incidental inputs such as the output directory, so any single `-fno-...` flag appeared to
fix it by luck. `-dcore-lint` named the real culprit: the Float Inwards pass produces an ill-scoped
coercion variable on code full of `unsafeCoerce`. `-fno-float-in` is stable across four builds and
costs nothing measurable on eight programs (`while_loop`, `struct_update`, `typeclass`, `hashmap`,
`string_chars`, `tuples`, `list_mergesort`, `functor_tree`: all within noise), so every generated module
now carries it.

**Collector settings, by scenario** (best of 3, seconds):

| RTS options | 15M-element array loop | array map/filter/fold | list functions |
|---|---|---|---|
| `-A128m` | 0.98 | 0.25 | 0.25 |
| `-A256m -O1g` | 0.81 | 0.20 | 0.17 |
| `-A512m -O2g` | 0.68 | 0.20 | 0.12 |
| `-A1g -O2g` | 0.60 | 0.22 | 0.14 |
| `-H2g` | 0.63 | 0.26 | 0.22 |

Larger is faster for programs with large live data, and costs peak memory.

**Heap census (`+RTS -hT`, normal collector, as tenet-hs advises).** No thunk leftovers anywhere,
which was the lesson most worth checking. The live data is the boxing we already knew about: the
15M-element array loop holds 240 MB of `W#` boxes plus a 134 MB pointer array; the tuple fold is cons
cells and `W#` boxes; `list_funcs` adds about 50 MB of persistent-array version records (`Arr`, `Diff`,
`MutVar`) and 39 MB of stack. Sharing preallocated boxes for small values would not help these, since
the values are large.

## const_fold: where 26.5 G instructions went (and why wall time was level)

`bench/realworld` `const_fold` retired 26.5 G instructions against native Lean's 16.5 G (1.59x) while wall time
was about level, because cycles were equal (5.1 G vs 4.9 G): the extra instructions were cheap, high-IPC ones.
Measured with `/usr/bin/time -l` (instructions retired, deterministic) and by running `Out.Fast` and
`Out.Exact` separately (a throwaway `Main` that calls `F.z_entry` or `E.z_entry`):

| part | instructions retired |
|---|---|
| word run (`Out.Fast`), overflows at the last step | 10.5 G |
| exact rerun (`Out.Exact`), before | 16.1 G |
| total (the two add up) | 26.5 G |

1. **The answer does not fit in a word, so the work ran twice (10.5 G of 26.5 G).** `entry` returns
   `a * 2^40 + b` and with 500 repetitions `a` exceeds 2^24, so the final `natMul` throws `ZOverflow` after the
   whole word run is done and auto mode reruns everything exactly. This is the documented "auto mode may run a
   call twice"; nothing here is specific to the loop. It is NOT fixed: avoiding it needs either a per-value
   word-or-big representation (taxes every operation and every constructor field) or splitting the root so only
   its final arithmetic is exact. Cheap to avoid in the program itself (return the pair, or smaller digits).
2. **The exact path called out of line for every operation (3.5 G saved).** `Out.Exact` compiled `natAdd`
   to a call of `GHC.Internal.Bignum.Natural.naturalAdd` (and `naturalSubThrow`, `naturalMul`, ...), each
   re-testing both operands. Now `Zempic.Nat.Exact` matches `NS` in line (add/mul with the overflow flag, sub
   with a compare, quot/rem, eq/lt/le) and sends only the big case to a `NOINLINE` function. Exact run 16.1 G
   to 12.6 G, and 1.04 s to 0.66 s user. This helps every program that falls back to the exact path.
   The exact run is now below native (16.5 G) on this program.
3. **Tag tests and enters at every function entry (1.4 G saved on the word run, 10.5 G to 9.1 G).** A
   recursive function over `data Expr` (`appendAdd`, `eval`, `reassoc`) tested the pointer tag of its argument
   on entry although the caller always passes an evaluated value. GHC's `-fworker-wrapper-cbv` makes the
   strict-argument contract part of the worker, so the test is gone. It also helped `unionfind` (31.2 G to
   29.0 G). It is on for every generated module except when a function signature mentions
   `Word8/16/32/64/Word`: there it made `qsort` 15% worse (21.9 G to 25.3 G), because the worker keeps the
   boxed `Word32` arguments and SpecConstr no longer produces the all-unboxed loop. `deriv` (which has one
   `Word32` return type) loses its 3.7% for that reason.

Not the cause: allocation of `ZNat` (the fields are unpacked `Word#`; the word run's 10.6 GB are the
`appendAdd` copies, where native Lean reuses cells in place), GC (0.03 s), thunks (none: every binding is
strict), dictionary calls (none).

| `const_fold` (n = 500) | before | after |
|---|---|---|
| instructions retired (native: 16.5 G) | 26.5 G, 1.59x (recommended: 26.3 G) | 19.7 G, 1.19x (recommended: 19.5 G) |
| cycles elapsed (native 4.9 G) | 5.7 G | 4.4 G |

Same A/B method as above (`main` worktree vs this branch; instructions are the primary metric, wall time on
this machine was noisy: load from other jobs moved native itself between 1.3 s and 2.5 s).
